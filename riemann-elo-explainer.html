How grades & Elo work paired with v1.23.6

An honest write-up of what's actually behind the grade you see on the end screen, the badge on the profile, and the community-average number. With formulas, examples, and the bits I haven't implemented yet.

TL;DR

  • Grades are a ladder of 24 steps from 4A (Layman) to 11C (Nobel). The tier numbers are roughly logarithmic in real-world difficulty: each tier ≈ "one academic step harder".
  • Internally each grade is mapped to a decimal Elo number on a linear scale: Elo = 1000 + index × 100.
  • When players rate a game, the topic's running Elo is moved a fraction of the way toward the rating's Elo (exponential moving average, not classic pairwise Elo).
  • The "log-ness" lives in the grade ladder, not in the Elo update.
  • A >cap "higher than I can grade" vote nudges the running Elo up by half a step at half weight — directional only.
  • Per-rating weights are wired through but currently always 1.0.

The grade ladder

Each grade is a (tier number, letter) pair. Tier numbers run 4..11 and have human-readable names; the letters A, B, C are sub-positions inside one tier (A = top, C = bottom — A > B > C).

The ladder of 24 grade strings, in order:

4A 4B 4C  5A 5B 5C  6A 6B 6C  7A 7B 7C  8A 8B 8C  9A 9B 9C  10A 10B 10C  11A 11B 11C

Helpers in code:

const TIER_MIN = 4, TIER_MAX = 11;
const ALL_GRADES = (() => {
  const out = [];
  for(let n = TIER_MIN; n <= TIER_MAX; n++)
    for(const l of ['A','B','C']) out.push(`${n}${l}`);
  return out;
})();

function gradeIndex(g){
  // accepts "5B" (index 4) or whole-tier "5" (index 4 — middle of tier)
  const m = String(g||'').match(/^(\d+)([A-C])?$/); if(!m) return -1;
  const n = parseInt(m[1], 10); if(n < TIER_MIN || n > TIER_MAX) return -1;
  const pos = ({A:0, B:1, C:2})[m[2] || 'B'];
  return (n - TIER_MIN) * 3 + pos;
}

Three layers of "log-ness"

  1. Curriculum is log-flavoured: Layman → Middleschool → Highschool → Undergrad → Grad → PhD → Frontier → Nobel. Each step is many years of training, so the human difficulty is roughly geometric.
  2. Grades inside a tier are linear: A → B → C are equally spaced sub-positions, separated by accuracy thresholds (≥85% → A, ≥55% → B, else C).
  3. The Elo mapping is linear in grade index:
    Elo = 1000 + gradeIndex × 100
    So 4A = 1000, 5A = 1300, 6A = 1600, 11C = 3300.

Caveat — log scale, not log update

The TIER axis is approximately logarithmic in "difficulty years". The ELO axis is linear in tiers. The UPDATE rule (next section) is an exponential moving average, not the classic Elo win-probability formula. So strictly:

  • "Log Elo": no, the Elo math itself is linear.
  • "Logarithmic difficulty scale through tier names": yes.
  • "Classic chess-style Elo with K-factor and expected scores": no, it's EMA toward the rating.

The Elo update — what actually happens

Each topic + settings bucket carries a running Elo number. When a user submits a rating, that rating is mapped to its Elo target and the running value is pulled toward it by a fixed fraction.

Eloₙₑw  =  Eloₒₗ𝒹  +  K · weight · (Eloₜₐᵣ𝓰ₑₜ − Eloₒₗ𝒹)

With current constants:

ConstantValueMeaning
GRADE_ELO_BASE1000Elo at the bottom of the ladder (4A)
GRADE_ELO_STEP100Elo per single grade step
ELO_K0.20Learning rate per rating (20% pull toward target)
DEFAULT_RATING_WEIGHT1.0Default per-rating weight; pluggable per future content

The two helper functions in source:

function gradeToElo(grade){
  if(grade == null) return null;
  const s = String(grade);
  if(s.startsWith('>')) return null;   // directional, handled separately
  const idx = gradeIndex(s); if(idx < 0) return null;
  return GRADE_ELO_BASE + idx * GRADE_ELO_STEP;
}

function eloToGrade(elo){
  if(elo == null || !isFinite(elo)) return null;
  const idx = Math.round((elo - GRADE_ELO_BASE) / GRADE_ELO_STEP);
  return ALL_GRADES[Math.max(0, Math.min(ALL_GRADES.length - 1, idx))];
}

And the update step itself:

function eloApply(current, grade, weight){
  weight = weight || DEFAULT_RATING_WEIGHT;
  if(grade == null) return current;
  const s = String(grade);
  if(s.startsWith('>')){
    // "Higher than I can grade" — directional bump at half step / half weight.
    const base = (current == null ? GRADE_ELO_BASE : current);
    const target = base + GRADE_ELO_STEP * 0.5;
    return base + ELO_K * 0.5 * weight * (target - base);
  }
  const target = gradeToElo(s);
  if(target == null) return current;
  if(current == null) return target;     // seed on first rating
  return current + ELO_K * weight * (target - current);
}

That formula is exponential moving average: each new rating brings the running value 20% (×weight) closer to its target. Many ratings of the same grade converge to it; mixed ratings settle toward a weighted geometric mean of them.

The "Higher than cap" vote

Some users feel a game deserves a higher grade than they personally can give (their own cap is set by the 3× unlock rule). Letting that vote map straight to "one tier higher" would be wrong — they aren't actually claiming a specific tier. So it's treated as a direction:

Eloₙₑw  =  Eloₒₗ𝒹  +  0.5 · K · weight · (½ · STEP)

That is — half the K, half a grade step. Many "higher" votes pile up and eventually move the Elo by one full grade; one vote barely registers. The community line reports them separately as "N say higher" so they don't pollute the concrete-rating count.

Per-rating weights

Every rating carries a weight, default 1.0. Today every rating uses the default, so the system is effectively unweighted. The plumbing is in place for two future ideas:

  • Tier-weighted: a rating from a 9C player on a Highschool problem could be discounted (they probably can't tell 6A from 6B for the local audience), while a 6B player rating a 6 problem counts at full weight.
  • Confidence weight: a rating cast right after a perfect run counts more than one after a 0% run.

Example 1 — Settling onto 6A

Bucket starts at Elo 1500 (= 6C). Eight users in a row submit 6A (Elo 1800):

step 0:  Elo = 1500
step 1:  Elo = 1500 + 0.20 × (1800 - 1500) =  1560
step 2:  Elo = 1560 + 0.20 × (1800 - 1560) =  1608
step 3:  Elo = 1608 + 0.20 × (1800 - 1608) =  1646.4
…
step 8:  Elo ≈ 1749   (grade reading ≈ 7B, but they all said 6A — so this floors to 6A)

Two takeaways: (a) one rating doesn't pin the grade — it gets the average a fraction of the way there. (b) consensus pushes the Elo steadily toward the consensus grade. Several Hundred votes are needed to lock anything in.

Example 2 — Mixed votes

Two users say 6A, two say 5C, one says >6A. Starting Elo 1500:

vote 6A   target 1800 :  Elo = 1500 + 0.20×(1800-1500)   = 1560
vote 5C   target 1500 :  Elo = 1560 + 0.20×(1500-1560)   = 1548
vote 6A   target 1800 :  Elo = 1548 + 0.20×(1800-1548)   = 1598.4
vote 5C   target 1500 :  Elo = 1598.4 + 0.20×(1500-1598.4) = 1578.7
vote >6A  half-step bump:  Elo = 1578.7 + 0.5×0.20×0.5×100  = 1583.7

Lands between 6C and 6B with a "1 higher" tally on the side.

Where it's used

  • Community line on the end screen ("Community: 6A · 4 ratings · 2 say higher") is the result of communityRatingFor(topic) — it walks every local user account, replays their bucket ratings through eloApply, and converts the final Elo back to a grade via eloToGrade.
  • Best grade pill on profile rows is unrelated — that's the player's own highest earned grade (system's pre-determined grade from gradeFor(accuracy, diff, topic)), not the Elo of community ratings.
  • Average grade per user in the username chip uses each discipline's highest-earned grade and averages by ladder index. No Elo here either — it's plain index averaging.

Honest list of what's NOT yet implemented

  • Classic Elo with expected scores. Real Elo asks "what's the probability that A beats B?" via 1 / (1 + 10^((Rb-Ra)/400)), then updates both ratings by K × (actual − expected). We don't have pairwise games yet, so the formula collapses into the EMA above.
  • Two-sided updates. The player's own rating doesn't move from rating a topic. Only the topic's Elo moves.
  • Confidence intervals / posterior. A topic with one rating is treated like a topic with a hundred — there's no notion of how settled the Elo is.
  • Time decay. Old ratings have the same weight as new ones.
  • Logarithmic Elo. The Elo axis is linear in grade index, not log. If you'd want each tier to be a 2× difficulty jump in Elo terms, the mapping would become Elo = BASE × 2^tier instead of BASE + idx × STEP.

Migration / storage

Ratings live inside each user's profile, scoped to a settings bucket:

user.byTopic[topic].bySettings[sig].ratings = [
  { grade: '6A', weight: 1.0, ts: 17... },   // future shape
  '6A',                                       // current shape — string only
  '>6A',
  …
]

The reader accepts both shapes. Schema for the user object is at version SCHEMA.user = 3; the next breaking change to the rating shape will bump it again and the per-object schema gate will refuse stale data without nuking the whole account.

Summary in one paragraph

Grades are a 24-step ladder mapped to a linear Elo scale (1000 + idx×100). When a player rates a game, the topic's running Elo is pulled 20% toward the rating's Elo (weighted EMA, not classic chess-style Elo). "Higher than my cap" votes nudge the Elo up by a half-step at half weight. Per-rating weights are wired in at 1.0 for now. The community-average shown to other players is just eloToGrade of this running Elo, plus a separate tally of "higher" votes.
